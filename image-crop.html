How many bytes a crop actually removes

Cropping deletes pixels, so the saved file has to shrink — just not in proportion, and on a flat graphic it barely shrinks at all. Each row below is a real measurement: decode the file, draw the crop box onto a canvas, write the result with canvas.toBlob(), read Blob.size. The source is a 1200×630 PNG that weighs 44,915 B, and every box is anchored to the top-left corner so each row keeps less of the same picture. Headless Chromium 149.

Half the picture gone, and the file is still 101% of the one you opened. Crop this PNG to half its area and save it as PNG and you get 45,322 B against the original 44,915 B. The reason is that the crop is the cheap half of the job: the expensive half is writing a fresh PNG of whatever is left, and a full-frame re-save of this same picture already costs 71,663 B (160%). Savings only become real further down — 25% area keeps 52% of the bytes, 1.8% of the area keeps 4%. So do not budget a crop by area.

At the same pixel count, cropping is smaller than resizing down. Same two operations, same output dimensions:

Resampling repaints every pixel it keeps — the flat areas pick up gradients that PNG then has to store — while a crop keeps the original pixels of the region you want. If the goal is “a small piece of this picture”, crop first and resize only if the result is still too big. If the goal is the whole picture at a smaller size, that is the resize tool and its own byte table.

Where you cut matters as much as how much you cut. The same 600×315 box, moved around one picture: top-left 23,517 B, centre 27,972 B, bottom-right 21,711 B as PNG — a 29% spread — and 24,528 / 32,714 / 23,798 B as JPEG, a 38% spread. Same area, same encoder, same file. Any claim about what a crop saves that does not say where the box sat is worth nothing.

A PNG crop costs no pixels; a JPEG crop costs one more generation. Comparing every saved crop against the exact source pixels it was cut from: PNG differs by 0.000 levels of 255 in all seven sizes (lossless, byte-exact), while JPEG at .92 differs by 0.78–1.29 levels depending on the box — the same order as a first JPEG encode, which is what the JPEG table measures. Staying in PNG is the only path that adds nothing.

Cut a quarter out of a 199 KB photo and the PNG you get back is 374,088 B — 1.84× the file you dropped in. All four rows are larger than the source, which is why this page always hands back PNG: it is the format that preserves what you kept, not the format that saves space. If the smaller number is what you actually need, that is an encoding decision, not a cropping one: the same quarter crop as WebP .85 is 36,808 B, 18% of the original, and the JPEG vs WebP table covers the quality side of that choice.

Measured on one flat graphic and one photo-like JPEG, one browser build (HeadlessChrome 149) and canvas.toBlob(). Photos, screenshots and artwork land on different absolute numbers — treat the directions here as the finding and the bytes as examples.

A crop is a copy — until the box lands between pixels

Everything above assumes a crop box whose corners sit on whole pixels, and that is what a canvas needs to hand back the original pixels untouched. Until 2026-11-27 this page did not guarantee it: the box lives in source-image coordinates and a drag converts screen pixels to source pixels by the display scale, so the numbers in between are fractions. On a 4000×2667 photo shown at 600 CSS pixels wide, one screen pixel is 6.67 source pixels, and a 13-pixel drag produced x 1850, y 1233.5, 386.667 × 286.678. drawImage() takes those as written and samples between rows instead of copying them.

How much that costs, measured with a picture that cannot hide it. A 1200×800 test image filled with a 1-pixel checkerboard — black and white alternating per pixel — is the worst case any resampler can meet. Same 300×200 box every time, only the corner moved:

Half a pixel in either direction erased the entire pattern — all 60,000 pixels came back as the same grey, 127, because every output pixel was the average of two neighbours. Half a pixel in both directions gave the identical file. And note the direction of the byte change: the blurred copy is 19% smaller, because a flat grey field compresses better than alternating black and white. A smaller file is not evidence that the crop was clean.

The fractional part of the size alone, with a whole-pixel origin, cost nothing: asking for 300 × 200.75 at (100, 100) returned a file byte-identical to 300 × 200, because the canvas truncates the height and the extra 0.75 row is simply clipped. It is the fractional origin that gets sampled.

On real pictures the same thing happens at a smaller amplitude. A 16:9 crop from the page's own ratio button lands on 300 × 168.729 starting at y = 315.625. Against the nearest whole-pixel crop of the same region:

The one thing a snap cannot fix is the aspect ratio. The saved file is whatever whole-pixel size the canvas is given, so the five ratio buttons are only as exact as their integer arithmetic. At the default 300-px width:

Truncation and rounding both land on the same 225 for 4:3 — the button asks for 1.333, which is 0.006% under 4/3, and the integer lands on 300×225, exactly 4:3. 16:9 is the one that used to hurt: the file said 1.7857 against 1.7778, and now says 1.7751, which is closer. A single a few-hundredths-of-a-percent error is invisible in one crop and compounds across repeated crops, so if a frame must be exactly 16:9, set the pixel size in the resize tool instead of trusting a ratio button.
