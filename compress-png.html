What a PNG re-encode actually does

PNG has no quality knob, so “compress PNG” has to mean something else. We took one 1200×630 graphic and one 1200×800 photograph, stored each of them several different ways — same pixels every time, different file — and ran every copy through the panel above in headless Chrome 149. The output never varied. These are measurements, not estimates:

Same pixels, seven different source encodings — output size depends only on the pixels

Graphic — zlib level 6 (Pillow default)47,020 B71,663 B+52.4%
Graphic — zlib level 9, optimised44,915 B71,663 B+59.6%
Graphic — level 9 + 6 metadata chunks45,240 B71,663 B+58.4%

All four graphic sources produced the same 71,663 bytes, and all three photograph sources the same 2,150,964 — byte for byte, matching SHA-256, not merely similar sizes. That is the whole finding: this is not a compressor, it is the browser's own PNG writer, and its output is a function of the pixels alone. Nothing about how your file was stored survives the round trip.

So a PNG re-encode helps exactly once: when the file you start with was stored lazily. That stored copy went from 2.27 MB to 70 KB, which is a real 96.8% saving and the reason “PNG compressor” tools appear to work at all. On a file that came out of a normal export the same treatment costs you 52–60%, and the panel above will still print the word Compressed next to the bigger number — only the sign of the percentage tells you which way it went. A file that grows under “compress” is telling you it was already compressed.

The quality argument does nothing at all

The Canvas API accepts a quality argument for every image type, so we passed one deliberately, four different values plus no argument at all, on the same canvas:

Every row is the same bytes, not just the same size. Any PNG tool with a quality slider is either showing you a number that changes nothing, or it is quantising the image to a palette behind your back — that second thing is real (PNG-8 with 256 colours), it throws colours away, and no browser canvas can do it. This one does not, and says so.

What does come off, and what it is worth

The only thing removed is everything that is not a pixel. We gave one copy a realistic wrapper — two text chunks, two international-text chunks, a physical-size chunk and a 110-byte EXIF block — and parsed the download chunk by chunk:

Metadata stripping is real, and it is worth 325 bytes — 0.72% of a small file — while the re-deflate that replaces it added 26,748. If your plan is “strip the metadata to get a smaller PNG”, you are optimising the rounding error. The good news is the other column: zero levels of difference in every pixel, so the lossless claim survives the trip. What it costs you is your EXIF (camera, timestamp, GPS — the JPEG page measures that block being deleted outright) and nothing else about the picture.

The lever that actually works: fewer pixels

If the goal is a smaller file, dimensions are the only honest control a browser gives you. Same two images, scaled in the same decode → canvas → toBlob("image/png") chain:

Halving the dimensions of the graphic saved 51.5% of its bytes and halving the photograph saved 72.6% — while a full-size re-encode added 58.4% and 35.4%. The second lever is the format: the same pixels as WebP at quality 0.85 are 27,792 bytes for the graphic (38.8% of the PNG the browser wrote) and 215,206 for the photograph (10.0% of it, and 13.2% of the 1,627,250-byte PNG that went in). Both controls live one click away — use Resize Image to drop pixels, JPG to WebP to change format, and Compress JPG if the picture is a photo and can afford to be lossy.

⚠️ Boundaries. Two images, one browser build (headless Chrome 149), sources written by Pillow; a different browser may write a different deflate stream, and a dedicated PNG optimiser (zopfli, pngquant, oxipng) will beat every number here because it is allowed to change the encoding — or the palette — in ways the Canvas API cannot. The directions hold: output depends on pixels, quality does nothing, metadata is worth less than a rounding error, and dimensions are the real lever.
